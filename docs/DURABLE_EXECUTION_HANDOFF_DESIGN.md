# 耐久执行交接

阶段 `T-durable-execution-handoff`，基点 `3906c1f290610194d69d708d549ead75d8eabf10`。沿用用户已确认的正式项目/需求/任务/执行权威、紧凑工作台及“先完善源码、资源窗口恢复后验证”的顺序。本设计不要求新基础设施，不新增业务任务模型，不自动启动进程。

## 决策及可观察行为

`execution.queue` 在同一 Manager SQL 事务和项目版本检查中保存执行意图 E、唯一技术交接 H、事件和原命令回执。E 仍是正式业务资源；现有 ACK 的 execution 资源和 `result:null` 足以证明请求已耐久受理，不代表外部计划存在。界面显示“已受理，后台准备计划”，释放表单及离页保护，随后按精确 E 读取交接状态。

H 不复用项目全局版本作为领取身份。它保存项目/租户/E/任务/工作区/原请求者、完整固定请求及摘要、受理版本、技术状态、单调 fence/revision、尝试次数、租约、下次尝试时间、有限错误及真实运行引用。每个 E 只有一个 H，不能通过新的 H 或新的外部键重复派发。新表及全部字段通过项目 SQL 写保护；身份和固定请求不可变，技术变化仅限交接服务。

后台通过已存在的 Manager 同步生命周期扫描有界到期 H，先在短 SQL 事务中领取并提交，再处理同一个固定请求。真正创建计划前重新检查原请求者当前有效身份、项目写权限、运行 execute 权限、项目 active 状态、完整任务/需求依据、依赖、成员绑定、工作区/Agent/目标版本及先前停止证据。不会用系统身份替用户取得新的执行权。权限政策保持现有定义，不顺带扩展角色。

已有外部事实的正向恢复与新派发资格分开。内部恢复只能读取原租户/业务/工作区/原请求者/原 H 的不可变收据，不授权新的工具执行；可记录既有事实为历史证据，不能把失效任务重新置为完成。技术事实维护在归档项目中使用窄能力，不能全局绕过归档写保护。

## 执行器原子边界和关闭

仅有 SQL 租约不能阻止失联旧 worker 继续向另一个存储写入。Core 必须拥有同库的受控交接门：范围固定到 tenant/business/workspace/project/E/H/actor，校验完整请求摘要、单调 fence 和单向关闭状态。此门不暴露为任意可编辑业务资源。

一次受控派发在同一 Core 事务内完成门检查、运行任务信封、planned run、标准派发收据及交接收据。复用正式命令/单 Agent 计划生成及目标/配置验证；抽取接收现有连接的内部函数，独立工作区调用继续经过同一正式实现。失败回滚全部，不留下“信封已建但计划未建”的半份受控派发。计划创建不运行命令、不执行 Agent、不创建进程。

完整受控原件包含信封与验收快照，独立限制为 1 MiB UTF-8；超限在受理时明确拒绝，不能截断原件。浏览器恢复槽字符预算和独立工作区的派发正文预算仍分别适用。受控后台计划目前仅支持 workspace 隔离；独立工作区的 git_worktree 路径保留原能力，不能绕过受控协议启动进程的限制。

正式派发的新增计划分支先锁工作区、再锁任务与配置，Agent配置按ID稳定取得；节点和角色执行顺序保持原定义，回放既有收据仍可先返回。此调整消除本次事务复用引入的Agent/任务反序。既有执行校验仍有Agent先于目标工作区的路径，整个Core的运行并发锁图及多数据库行为仍待独立核验，不能从本次派发顺序推导全局无死锁。

取消未启动交接必须先在相同 Core 门上关闭。关闭与建计划串行：若关闭先成立，任何迟到 worker 都不能再创建；若计划已存在，返回真实计划引用，调用者必须按实际运行重新确认停止，不能回执为 not_started。Core 不可达或结论不确定时保留未确认状态，不凭缺少收据确认停止。关闭结果和计划收据只能正向恢复，不能撤销或改写既有事实。

## 投影、重试和版本

Core 已提交而 Manager 投影失败时，H 的已提交领取记录仍存在。下一次处理按同一固定 H/摘要恢复 Core 收据，在当前项目版本及 H fence 下投影已有引用。其他业务命令推进项目版本只引起投影重试，不要求重放旧项目版本的 sync，也不改变原 queue 的受理 ACK。

领取租约和重试状态使用 H 自身 revision；过期领取使用更高 fence。旧 worker 不能覆盖新领取或取消结果。SQL 项目锁串行取消、生命周期及实际投影；不得把外部操作和未提交的初次受理混在一起。重试使用退避和有界错误；不重建正文、换目标或换外部幂等键。配置失效等明确阻塞需要用户查看原因、取消旧意图并重新准备，不能静默采用最新配置。

`execution.sync` 改为观察并持久化已存在运行事实，不能创建信封或计划。`execution.review` 必须已有真实运行与固定版本证据，再按原有依赖/测试/人工验收规则处理，不能先隐式派发。自动交接与同步不自动启动；启动/重试/审批仍使用现有固定预览和独立授权。

## 读取与交互

精确交接读取提供 `project_id`、H/E/任务/工作区身份、状态、revision、attempt、受理/更新时间、下次尝试时间、有限错误和已证实运行引用。列表投影显式携带有界交接摘要，Agent 运行中心与任务详情使用同一事实。

任务详情提供单一“当前交付”状态及主要动作：已受理/后台准备、受阻、计划已建待启动、运行、测试结果、待验收。运行/测试/验收分别读取真实事实，不按百分比猜完成。后台已受理受阻与 HTTP 回执未知分开；前者不持续拦导航，后者继续恢复原请求。技术明细按需展开。

受理事务中的 canonical task→H→E 关联用于独立任务定位读取；项目权限仍由服务端校验，执行身份受当前工作区读取资格保护，真实403不得通过定位接口绕过。精确恢复入口不依赖派生索引可用。冷任务定位的所有消费者必须随最终实现核验，未接通的入口继续记录为待办。

## 方案取舍与限制

采用完整耐久交接及 Core 关闭门，优于仅追加正向修复命令：后者只能处理完整外部收据已有的情况，无法给新派发及负面停止结论建立可靠协议。E 资源 ACK 保持既有合理语义，不为了多一个操作标识扩大所有客户端的写合同；H 从精确 E 读取。

不以新协议伪造历史未知命令的原 ACK。旧 sync/control 已发出且原 Manager 回执缺失的记录，若因原全局版本无法恢复，仍需独立、授权且可审计的对账结论；不能拿新 H 状态冒充旧命令成功。部署、运行控制等其他跨存储边界同样需要分别核验，不能从本次派发改造推导全链路已可靠。

具体仍保留的控制窗口：待派发取消先在 Core 成功封门、Manager 事务回滚，随后后台恢复关闭事实并推进项目版本；原取消请求会因原版本过期而缺少自己的 Manager ACK。封门已阻止迟到派发，但不能将关闭事实当成原取消命令已确认。界面继续保留原控制请求，后续以独立耐久控制意图或正式授权对账协议处理。

## 验收证据

源码定义应覆盖：受理事务回滚零外部效果；同键重复受理；两 worker 领取/fence/过期；Core 原子回滚；外部提交后 Manager 回滚且其他命令推进版本；进程重启恢复；关闭先后与迟到 worker；撤权/归档/失效依据；观察和验收零隐式派发；相同 H 的真实状态及消费者；SDK/CLI 保持真实原件透传。执行器独立工作区必须保留原行为。

按用户要求，本阶段先源码和定义，标准库文本/JSON/AST/摘要及独立源码审查可运行；应用导入、测试收集/执行、类型、构建、浏览器、服务和外部工具运行均等待资源与共享验证窗口。源码阶段提交不等于运行、生产或全目标完成。
