# 任务验收与独立执行

基线 `5fb9f77`。本阶段落实唯一业务 Task 的自身验收条件，并让独立任务使用同一原生派发、测试、人审和问题回流。用户已授权紧凑协作工作台、合理目标设计、阶段验证后全部提交且不推送；不新增兼容别名或假需求。

## 数据与行为

SQL `Task.acceptance_criteria` 为任务自身的文本条件，最多 80 项、每项 2000 字符，去除首尾空白、拒绝空项和非文本。需求关联单独使用 `requirement_criteria_indices`，仅为当前需求条目的唯一非负整数下标。模板、AI 输出、Delivery API、普通任务 API、同步、SDK 与 CLI 统一此命名。有效条件为任务自身条件加明确选定的需求条件；不静默继承整份父需求。

独立任务没有需求，需求关联为空。带需求 ID 但需求不可访问或已转属时属于来源失效，不能变成独立任务。需求条件改变后，旧关联不自动按新数组重新绑定；用户明确采用当前来源。空条件可保存草稿，派发和人工通过前必须补齐。任务自身条件与需求条件来源在详情、执行预览和原始证据中可见。

共享纯交付定义包含任务文本、自身条件、稳定负责人、可选需求快照、明确关联与依赖依据；不含正常生命周期状态、日期或资源预留。原生快照的 `requirement` 为真实对象或 null，不使用空名字模拟需求。人工验收仍记录登记状态，但使用相同条件来源。任务条件、需求关联/归属及依赖定义变化，在同一事务中永久使旧原生和人工证据失效；A→B→A 不恢复旧验收。单纯改期不作废验收。

独立任务测试证据留在已有 execution/results/review，关联需求时才生成该需求的测试产物。失败复用唯一 Issue 与转需求能力。任务删除/转属后保留原历史证据，旧运行不能修改新作用域任务状态；有权限的人可取消旧运行以重新派发，取消仅关闭旧执行，不改任务新状态。普通 CRUD、同步、导入、ORM/Core 写入均使用共同校验与事务捕获；GET/preview 仍纯读。

正式结构升级为显式、幂等、可核验的操作；新数据库直接创建新列。已有任务升级后自身条件为 []，不制造历史条件或通过记录。LanceDB 数据迁移与数据库结构升级分别命名。

## 四个界面与交互

1. 未准备：独立/需求来源、标题、负责人、登记状态与有效交付状态置顶；自身条件和需求关联分开，缺失条件有原因和编辑入口。
2. 编辑与预览：逐条维护任务条件、明确选择需求条件，依赖和日期沿用原计划编辑；同一执行编辑器预览真实条件、目标、固定 Agent 与测试。并发失败保留草稿，明确采纳最新依据。
3. 执行与审查：需求页与独立任务页共用任务内容和执行组件，实现、测试、人审分别呈现；出现原生运行后不能通过人工登记入口绕过原生审查。
4. 失败与历史：当前失败/失效优先显示，历史折叠保留原始来源；Issue 返回精确独立任务或需求任务。明确删除、转属、权限不足和读取失败，390px 单列、按钮换行、日志独立滚动、键盘可达。

团队登记与 runtime 身份绑定继续列为后续能力：稳定 member ID 绑定 workspace 与 AgentProfile ID/版本，设备只是执行位置；绑定不授予运行权限，不按同名推断身份。本阶段不冒称已完成团队执行身份或所有生产平台接入。
