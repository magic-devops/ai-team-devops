# 运维建议纳入正式处置链

T-ops-remediation-intake，基点 fb6ff3d934f3e21660a457b1579ed266f81c9e87。当前按用户安排仅做源码实现，所有运行验证后置。

## 事实与边界

旧自愈页面会固定提交 command_exit_code=0、status=healthy；旧后端仅写 JSON 就返回 applied/verified/rolled_back。这些是状态登记，不是执行或探针结果。现有正式 Issue 诊断、人审需求采纳、任务派发/测试/验收、受控部署与独立健康探针已形成主链，本轮将运维建议接入该链，停止维护另一套假执行状态。

## 正式合同

新增纯读 GET /delivery/ops-actions/{source_id}/intake，核实当前租户、项目、账号与文件来源范围，返回固定脱敏来源快照、摘要、当前版本、可写权限及已纳入的 Issue。来源读取有明确大小限制，拒绝路径穿越、缺失作用域、坏 JSON 和超预算；不截断后冒充完整来源。所有建议与旧成功标记均标为 reported_only，不具有部署或执行证明效力。

新增 issue.ops.intake 交付命令，携带 source_id/source_digest/title/description/severity，复用原 expected_version、原幂等键与正式事务回执。在项目事务内重验来源，固定快照与 Issue 同时写入。来源用独立、按租户/项目/来源唯一约束的追加式 SQL 表保存，不膨胀全项目 Workspace JSON；同问题来源有独立索引读取，通用 ORM/SQL 不能改写或删除固定来源。相同来源仅对应一个 Issue，换键不重复创建；原键重放优先恢复原回执，不依赖可变旧文件仍存在。旧来源变化时不自动换摘要或基点，需明确重新读取并采纳。来源已纳入后仍保留原快照，之后的旧 JSON 状态不能改变既有问题事实。

Issue 证据增加 ops 类型，供既有诊断选择使用；明确其为运维建议/自报数据，不能把其中的健康、退出码和审批人当作执行证明。问题可通过既有诊断/人审采纳形成需求，再拆解任务、派发人或正式运行资源、测试验收。部署与回滚继续由正式发布链和独立探针判断，Issue 不因建议登记自动关闭。

## 界面

Runbook 归集统一声明为来源记录覆盖率，不能作为执行、健康或验收证明。历史和新自愈记录均按 reported_only 展示，不能填平正式执行证据缺口；纯读投影也覆盖已保存的旧记录，不等待重写或回填才纠正误导。确认和归档只管理来源记录。来源 JSON 同时拒绝非有限指数数值、重复键和无效 UTF-8 字符串，异常数据返回明确拒绝，不进入快照或触发页面 500。

沿用紧凑工作台：保留策略、信号与决策预览；建议详情显示来源、风险、完整固定输入预览与单一“纳入问题”入口。已纳入则打开原问题。旧 applied/verified/rolled_back 只作为旧记录值展示，不以绿色成功或完整进度条呈现。不再提供固定成功、假回滚和重复生成治理任务按钮；受控发布入口保留当前项目。

纳入命令在发送前保存原请求，同一授权标签页会话可恢复未知回执；原件未知时锁定输入，失败保留草稿，确认成功后明确应用。区域切换不另建请求；当前项目/账号变化后的回调失效。恢复入口在列表或原来源读取失败时仍可用。

## 本阶段不宣称的结果

没有自动执行旧 action 字符串，没有按工具名称推断适配器，没有生产部署或自动闭环验证。真实自动运维策略编排仍需正式权限、固定执行计划、恢复与停止证据，继续列为待办。SDK/CLI 与接口合同同步，源码审查不能替代测试、类型检查、构建与真实浏览器验证。
