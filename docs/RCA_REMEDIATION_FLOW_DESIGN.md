# 根因分析进入正式处置

T-rca-remediation-flow，基点 c3686a5f40b244d97f902640e800d539cecd8d7d。沿用已确认的紧凑工作台和全流程建设要求。本阶段先完成源码，测试、类型、构建和浏览器验证等待人类恢复窗口。

## 问题和设计选择

旧根因分析页面固定提交 service/metrics/pipeline=healthy，再调用只登记 JSON 的验证接口关闭记录；手动关闭和重新分析后直接生成任务也绕开正式问题、需求和交付链。来源记录中的 resolved、passed、分数和 Runbook 关联都不能证明实际恢复。

复用现有运维来源纳入模块，不新建另一条需求或任务主链。RCA 纯读入口返回完整脱敏、有大小预算的固定快照、摘要、项目版本及原问题。新增 issue.rca.intake，使用与 issue.ops.intake 相同的严格五字段载荷和原版本/键规则，命令 action 区分来源类型。两种来源共用追加式 SQL 原件，但 source_type/source_id 共同确定身份，相同 ID 的两类来源不会串到一个问题。原运维请求的正文与回执合同保持真实可恢复。

## 数据和边界

服务端只按明确枚举读取 rca 或 self_heal_actions，不由用户指定路径。来源读取、脱敏、摘要复验、原键回执重放、同来源去重、删除问题不重建和项目权限沿用一个实现。新的 source_type 字段加入唯一约束与精确追加能力；没有来源类型的实际旧表通过已有显式离线 schema apply 升级，保留原 Issue ID、摘要和原件，不在 GET 或启动时自动改数据。不维护旧成功状态写接口。

RCA 的 verify、resolve 和仅登记检查即关闭的核心函数退出；验证计划替换为正式问题处理入口。归因候选和任务预览保留，实际任务应先固定 RCA 来源、纳入正式问题，经人工诊断采纳需求后拆解、派发和验收。旧 RCA 成功字段仅显示为来源自报；Runbook 归集不能利用它们填平正式验收缺口。

## 交互

根因记录按列表展示事件、根因、影响、处置建议与来源自报提示；主要动作是“核对并纳入问题”，成功后打开原问题。共用来源核对弹窗、草稿、明确采用新事实、发送闩锁、会话原件、未知回执恢复和稍后继续。列表或来源加载失败不卸载恢复入口。项目/账号改变或迟到回调不能提交，来源类型改变后不能沿用旧预览。

移除“验证并关闭”“手动关闭”“直接创建治理任务”和假验证评分，减少平行操作。保留真实归因输入和预览；窄屏使用同一纵向列表、可滚动弹窗和现有主题组件，不引入新组件库。

## 实施和验收定义

先补充未运行的 HTTP、来源隔离、数据库升级、客户端回执和实际编辑回调定义，再改共用服务和界面。覆盖同 ID 不同来源、原请求重放、来源变化拒绝、append-only 保护、旧表不自动迁移、升级保留原件、旧关闭路由不可用、列表失败恢复和迟到回调失效。SDK、CLI 和 OpenAPI 同步。固定源码独立审查并精确提交本阶段增量，保护既有 86 项独立工作。

源码审查不证明运行通过。没有自动执行 RCA 建议、没有自动关闭正式 Issue，没有用名称猜工具能力；策略自动编排、真实运行/探针和生产全流程仍需进一步实现和验证。
