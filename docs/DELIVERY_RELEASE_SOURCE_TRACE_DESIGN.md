# 发布代码与验收关联

任务：T-release-source-trace。实施基线：232144fc032543ec5f684e8541503c7b281a63ec。

## 目的与事实边界

发布范围内的有效任务验收、源代码纳入、构建测试、发布批准、部署验证分别证明不同事实。当前签名 CI 固定了最终 HEAD 与质量范围，但未证明已验收任务对应的代码仍在 HEAD。仅检查提交祖先关系不能发现后续回退。

用户已授权继续实现与设计，优先简化操作；当前只允许源码工作。本文和行为定义不代表实际测试、构建、浏览器或生产验证通过。

## 业务设计

发布准备者逐任务提出源码关联：配置中的发布仓库、完整的基准提交与验收提交、说明。非代码工作必须明确选择“不涉及代码”并说明理由，不允许系统从附件链接猜测提交。关联固定任务定义摘要、验收证明摘要。有项目批准权限的人在现有候选批准中一并确认这些关联；准备包和 CI 成功不能显示为已获人工批准。

源码关联保存在签名 CI 的原件和不可改写的候选快照中，复用现有唯一的候选批准、撤销和永久失效机制，不新增平行批准状态。导入与候选操作复用项目 CAS、原请求、幂等身份和严格回执。缺失的源码核对不能通过选用旧 CI 绕过。GET 和准备包预览不持久化状态；质量验收原事实保持独立。

## CI 核对

发布界面按当前显式选择逐任务填写关联，调用只读 POST `/releases/source-packet` 核对当前有效验收并下载受限大小的源码核对包，包含项目、仓库、策略代数、质量范围摘要及每个任务的固定关联。CI 生产器必须读取该本地文件，核对身份与摘要；网页不执行 Git、不获取私钥、不远程拉取仓库。

对于代码关联，CI 确认基准是验收提交的祖先、验收提交是实际构建 HEAD 的祖先，并比较基准到验收提交之间所有变更路径在验收提交与最终 HEAD 的树项。新增、删除、重命名、文件模式均纳入检查；后续改变或回退相关路径必须重新确认关联。路径数量和元数据量有上限；不支持的链接或子模块变更明确拒绝。允许与验收路径无关的后续提交。真实构建、JUnit 与制品摘要仍由原生产器核实。

签名谓词新增固定大小的核对包摘要、关联数量、核对路径数量与树摘要，不能用任意自报成功字段替代。生产器输出完整导入体 `{envelope, source_packet, requirement_ids, task_ids}`。Manager 导入时从当前验收重建核对包并比对摘要和签名；候选快照固定该包，批准界面展示完整关联。旧 CI 原件可查看，但没有当前核对证明时不能建立可发布候选。更换关联需要新的签名 CI；有效验收变化使原质量范围和 CI 失效。

## 交互设计

质量范围旁集中展示“验收 → 源码关联 → CI → 候选批准”准备步骤。源码任务逐条展示当前验收、仓库和提交，在同一工作台打开紧凑抽屉。仓库只读，提交输入使用明确标签，非代码选项展示理由。生成前核对固定验收，冲突后必须重新读取当前范围，不自动替换操作原件。CI 导入继续保留现有未知结果恢复，原件位于读取失败区之外。键盘、窄屏、加载、空态、无权限和失败状态必须可用。

## 实施与待验

1. 先补真实消费者的行为定义（当前不运行）。
2. 实现只读的明确关联核对包，复用原件、权限、失效和规范回执。
3. 实现受限核对包、CI 树核对和发布阻断，保持验收与部署含义独立。
4. 接通工作台、SDK/CLI，并补充当前共享契约和操作文档。
5. 独立源码审查、保留既有 86 项工作区改动、仅提交本阶段投影；测试窗口恢复后再执行真实验证。

待验证包括实际数据库、并发/重放、真实 Git 与构建、类型检查、端到端发布、窄屏与键盘和屏幕阅读器。源码审查只支持源码层面的结论。
