# 报告交接与草稿保护

阶段 `T-guided-delivery-handoff`，基线 `f05fe9c7c4ed7203f57ae987bd1b8ae9f4b13cf8`。沿用紧凑协作工作台、现有组件库和三语体系。用户要求优先完善源码和操作流程，运行、测试、类型、构建和浏览器验证继续后置。

## 实际断点

外部工单的持有人提交报告后，需要回到工单，再次选中刚保存的报告并确认停止、关联。两个独立操作之间的状态不能当作一次交付。任务详情中的多个表单共用一个编辑布尔值，只有工作区快照固定，没有导航保护；关闭一个编辑器也会清掉另一编辑器的固定快照。上层工作台部分跳转先修改本地选择，再更新路由，仅在 Task 内拦截浏览器事件不够。

## 一次交接使用原业务事务

规范入口仍为 `task.delivery.submit`，可显式提供：

```json
{"work_order":{"id":"W1","order_revision":2,"stopped_attestation":true}}
```

`work_order` 省略或为 null 时，仅保存报告。停止自述必须为实际 JSON true，不接受数字、字符串、缺失或 null。整份报告仍受原有 48 KiB 上限、逐条验收条件、证据关联和测试状态规则约束。

后端在保存前核实当前项目、真实 Task、持有人、明确工单与 revision、任务及完整原生关闭边界。形成唯一固定 S 后，复用既有 `work_order.report` 的原件、最新报告、持有人和新鲜度门禁，写入同一 S 关联及外部停止自述。整个过程使用一个原请求、版本、幂等键、事务和回执，不串联两次 HTTP，也不在内部提交。后半失败时，S、旧 S 失效、Issue、W、版本、事件、查询代次及回执一并回滚。

成功回执保持 S 为主资源，额外携带 `result.work_order={id,order_revision,state:"reported"}` 与明确 W affected ref。单独保存 S 的回执保持原结构。绑定的 W 原运行范围进入 S 原件和回执的权限核验；列表、历史和详情继续按当前授权读取。活动主目标使用真实 Task ID，不能把 S 或审核 ID 当成 Task。

`work_order.report` 仍用于关联已经保存的固定 S，例如先保留报告、外部工作稍后停止的情况。它使用同一报告原件和既有权限门禁，不新增第二种报告正文或完成状态。

## 四处交互

1. **任务报告表单**：展示当前可交接工单及执行资源，来源名称可编辑预填；停止确认默认不勾选。主操作为“核对报告并交接”，次操作为“仅核对报告”，说明后者保留工单占用。测试和验收结果仍由用户逐项报告，不能自动填通过。
2. **固定请求与恢复**：核对后展示明确工单、revision 和停止自述。发送前保存完整原请求；未知结果恢复原正文、版本、键和 W，不读取新 W 来替换。回执确认但本地清理失败时，继续完成清理，不重报新 S。
3. **工单与报告互访**：从正在查看的 W 填写报告时传递明确 ID/revision；过期按钮不能自动换成另一个当前工单。读取期间 W 或 revision 变化，需要明确采用当前依据并重新勾选停止确认，报告文字和证据继续保留。固定 S 可返回其关联 W。
4. **任务编辑与离开**：工单、原生执行、任务计划、设计、外部报告、人工审核各有稳定草稿槽。打开和关闭同步通知，单个槽关闭不会释放其他草稿。Task 和上层需求/抽屉导航均在修改本地选择前检查草稿。草稿导航保护与未知写入互斥分开，因此当前表单仍可核对、提交和关闭；丢失回执仍需恢复原请求。原生执行、任务编辑和协作写入分别通知，互不清除占用。普通任务编辑也启用原编辑器的发送及未知结果锁定，在表单仍挂载时重试相同值、版本和键；这不证明它已有跨浏览器重启的持久恢复。协作讨论沿其既有持久草稿和写入恢复机制，不宣称本阶段覆盖所有输入形式。

窄屏操作换行，沿用显式标签和键盘可聚焦组件；草稿阻止离开后展示处理提示。源码实现不能证明实际渲染与键盘行为通过。
