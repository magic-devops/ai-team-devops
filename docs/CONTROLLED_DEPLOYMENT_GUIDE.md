# 受控部署与恢复

在项目的「质量与发布」中打开已批准候选，明确选择环境，再核对固定计划。环境配置、部署批准、执行权限分别检查；配置了设备或工具并不表示已经授权运行。

## 配置环境

配置者需有项目 configure 权限和执行工作区的读取权限。环境名称须与候选中的环境完全一致，工作区必须属于同一租户。明确选择本机或已配对且在线的设备；远程设备的身份、能力及授权变化会要求重新核对计划，正常心跳刷新不会使预览反复冲突。

执行端需已安装 `hermes_core.deployment_runner` 和实际部署、独立探针工具。使用固定 argv，不经过 shell。API 不接收私钥、密码、TLS 绕过设置或手工健康数据。制品来源配置为明确 HTTPS origin，下载不允许重定向，并校验真实字节摘要及大小。CA 信任在执行端正常配置，仅对实际执行进程生效。

部署和探针 argv 可使用 `{artifact_path}`、`{artifact_sha256}`、`{commit_sha}`、`{operation_id}`、`{traffic_percent}`。未知占位符会被拒绝。运行时长必须覆盖下载、执行和整个观察窗口，灰度步骤严格递增且最终为 100。

独立探针每次退出 0，输出一份 JSON，例如：

```json
{
  "healthy": true,
  "artifact_sha256": "<实际制品的64位十六进制SHA256>",
  "traffic_percent": 25,
  "operation_id": "<本次固定操作ID>",
  "sample_count": 100,
  "observed_at": "2026-10-17T13:00:00+00:00"
}
```

示例中的值须由真实服务观测产生。制品、操作、实际流量、时间和样本均需匹配；只有执行命令退出 0、探针独立通过且达到观察时长和样本数，才建立验证结果。详情会保留真实失败探针的错误、耗时及有界日志。

## 从候选到发布

1. 核对候选的需求和任务范围、当前质量、签名 CI、提交及制品。暂停或筹划中的项目不能准备或发起新的部署副作用。
2. 预览并保存部署意图。固定候选、环境代次、设备依据、实际稳定基线和每个灰度步骤。
3. 明确派发，再明确开始。灰度步骤通过后等待人工晋级，不自动推进。
4. 100% 实际流量与健康验证通过，且候选仍有效、未被后续物理部署替代，才计入当前已发布需求。

输入提交失败会保留；版本冲突需明确读取并采用最新依据，不能后台改用新版本。网络结果未知时查询原请求或重放同一固定命令文件，不能生成新 key 偷换操作。普通运行重试、重放或修改不能绕过受控部署入口。

CLI：`sop delivery deployments`、`sop delivery deployments --id <id>`、`sop delivery deployment-preview --file deployment.json`。SDK：`delivery_deployments()`、`delivery_deployment(id)`、`delivery_deployment_preview(body)`。写入统一使用已有 `delivery command` / `delivery_command(body)` 的版本和幂等协议；动作与字段见 [部署设计](DELIVERY_DEPLOYMENT_DESIGN.md)。

## 失败、未知结果和回滚

已知命令失败保持失败。即使后来健康探针通过，也不能把已记录的非零退出码改写为成功。

执行进程中断、丢失结果或租约过期可能留下未知结果。执行端在副作用前持久化 journal；未知结果锁定环境，禁止自动重跑 apply。可查询原运行或明确执行只读观察。只有原操作证据与当前真实观测匹配时，观察才可能恢复已验证结果；缺少 journal、身份变化或证据不完整仍保持未知。

回滚是新意图，恢复原意图冻结的上个实际 100% 验证基线，再下载、校验、执行并观察。没有真实稳定基线或环境与目标不相容时不提供回滚成功捷径。回滚完成不会关闭原失败问题。

失败或未知结果在原事务中创建唯一项目问题。可以从详情进入排查，再沿已有问题转需求流程形成验收条件；重复同步或提交不会重复生成问题和需求。当前阶段不自动调用模型处置生产故障，也不未经确认修改业务。

旧 SystemOps 的执行、手工成功、JSON 灰度、回调和回滚登记入口已退出。环境配置导出仅作为配置包，旧流水线只读历史明确标记为历史，不参与发布验证。
