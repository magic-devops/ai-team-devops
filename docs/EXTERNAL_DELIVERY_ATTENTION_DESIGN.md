# 外部交付待办与直接处理

阶段 `T-external-delivery-attention`，基线 `0151490db2383fa43964088c2aae69f0bcc16525`。沿用已确认的紧凑协作工作台、AntD、主题和三语体系，不增加依赖。用户要求先完善代码和交互，应用、测试、类型、构建与浏览器验证仍后置。

## 已核实的断点

外部工单的实际业务进度已进入共享 `VerificationContext.delivery_status`，但待办只识别原生执行和登记完成后的人工验收：外部报告漏入待验收，自报受阻漏入受阻分类，任务负责人为智能体时实际接单人也可能看不到自己的工作。索引直接使用该投影，因此只改页面标签无法补齐事项和计数。

工单目录只显示生命周期和百分比，已有的人审结果、外部自报受阻及窄屏失效标记未充分呈现。“查看报告”还要先打开工单再转入报告。任务间导航复制旧查询参数，可能把另一个任务的报告、工单和自动填写标记带到新任务。

失败报告生成 Issue、人工退回关联 Issue、诊断和问题审查进入需求池已有实现。本阶段改善发现和处理入口，继续使用原问题回流业务。

## 同一个待办模型

- 在已授权项目的一次 `ProjectEvaluation.verification` 中派生薄 attention。新增信息只含当前有效 S、活跃 W、共享业务状态和接单人身份；不读取工作包原件、设计正文或进度日志，也不改变 Task 原件、负责人或 basis。
- 活跃工单先进入工作事项；自报受阻再进入受阻分类。排队不等于运行，取消待确认仍占用任务；即使原任务被手工改变，未收敛工单仍需可发现。保存 S 不会使尚未停止关联的工单提前进入待验收。
- 没有活跃工单时，最新有效且未有人审结论的 S，只有共享状态确认为 `awaiting_review` 才进入验收事项，`acceptance_kind=external`。人工退回后继续返工及已有 Issue 流程。失效、被替代的 S 不当作当前待验收。
- 原生执行与人工交付继续使用已有资格规则。无当前 S、无 E 且允许新的人工交付时，可以明确审查当期人工证据；旧外部报告不会自动成为它的证据或目标。
- 每个 Task 仍只有一条待办事实，多分类不重复累计总数。`mine_delivery_actor_id` 使当前可用人类交付参与人的工作、受阻事项进入本人范围；活跃 W 优先使用实际接单人，否则使用当前有效 S 的提交人，使人工退回后仍可发现返工与同一 Task 的问题。失效报告不携带旧参与人，新的活跃工单覆盖旧报告归属。该身份不赋予审批资格、不冒充 Task 负责人，不能把同名工具当作人类账号。
- 索引 schema 从 5 升为 6。当前 schema 的事实、分类计数、筛选与有签名游标保持同一代次；旧索引通过已有明确重建入口刷新，GET 不隐式重建或写库。

## 响应和定位

`InboxTarget` 增加可空 `submission_id`、`work_order_id`；非外部目标均为空。活跃工单优先定位 W；无活跃占用且有当前有效 S 时定位 S。目标只是定位标识，报告、工作包、原生运行和写动作仍在原详情入口重新核实作用域及权限。

SDK 仍完整保留服务器单页投影，不自动展开原件或下一页。CLI 的 JSON 保留全部字段，文字输出明确外部待验收来源及报告、工单编号；不会据此执行外部工具或提交验收结论。

## 四个关键界面与状态

1. 项目待办：在原工作、审批、验收、受阻分类中显示外部交付；外部待人审使用明确标签。点击时重新定位 Task，保留同一目标中的 S/W，任务归属变化和晚到响应仍按当前项目、会话核对。
2. 桌面目录：分别显示工单生命周期、自报进展、人审结果。受阻、待验收、已退回、已验收、已失效可直接识别。有报告时直接进入对应固定报告；其他情况打开精确工单。
3. 窄屏目录：与桌面复用同一事实呈现，失效状态不遗漏；长文本换行，操作可键盘聚焦。有进度但百分比为空显示“百分比未知”，没有进度才显示尚未报告，100%不等于人工验收。
4. 精确任务与返回：只有相同项目、相同 Task 的合法选择才沿任务内导航保留。改变任务、项目或离开任务时清理旧 S/W/自动填写标记；明确目标可以提供新的 S/W。独立任务绑定当前项目，并可返回原待办筛选与页游标。关闭、未知请求恢复和草稿保护仍沿现有原件机制。

目录只展示服务器已经返回的业务事实，不用本页过滤冒充整个项目的查询，也不据自报进度自动完成、停止或验收。
