# 项目规则

本文件是项目本地规则库的可追踪初始来源，依据根 `AGENTS.md` 和已确认的用户要求整理。用户会话中的明确指令优先。工作区恢复时仅在规则文件缺失时复制到 `.ai-memory/rules/RULES.md`，不覆盖已有人工维护或已采纳规则。

## 活跃规则

1. 当前仓库是建设主体。Multica、Hermes、WorkBuddy、OpenCode、Zed、Codex、Harness、dsh、OpenClaw作为参考，按实际业务需要复用或集成；不将参考名称当作已接通的证明。
2. 采用最合理的正式业务设计，去除不必要的历史分支。项目、需求、任务、执行、验收、版本、部署和问题回流共用稳定关联；保留独立工作区的真实使用能力。
3. 用户输入必须验证，项目及租户权限由服务端核实。禁止硬编码密钥，禁止将本地凭证、运行数据库、依赖缓存或会话日志提交到Git。
4. 执行成功、测试通过、人工验收和已发布分别记录。进度和图表使用真实业务事实；缺失历史、未知执行结果、未配置能力和未验证状态必须明确表达。
5. 写入使用明确的原版本、原请求和幂等身份。遇到超时或丢失回执，应恢复同一操作，不能将未知结果伪装成失败后另建请求，也不能伪装为成功。
6. 涉及功能或缺陷，先用覆盖实际消费者和合同的检查确认行为，再实现并验证。源码审查、模拟或历史结果只支持各自范围，不替代当前实际运行、浏览器或生产验收。
7. 界面采用已确认的紧凑协作工作台方向，保持项目上下文清晰，补齐加载、空态、失败、权限不足、断线、窄屏与键盘操作；直链、筛选和返回应保留用户工作位置。
8. 进度和限制持久化到 `memory/`，交付证据保存到项目约定的 `.sop-runtime/delivery-evidence/`。阶段性全部提交已验证成果，提交格式为 `type(scope): desc [T-id]`；未验证增量不能混作已完成成果。
9. 临时、测试、构建和源码副本优先放在仓库忽略的 `.cache/`。Windows短路径构建仅使用 `E:\tmp\cx\<任务>\` 下独立的 `src/out/tmp`，不得在盘根新建任务目录。环境变量覆盖仅作用于当前进程。
10. 清理前保留唯一用户原件、重要快照、截图和证据的清单与摘要；核实最终路径在本任务目录内，解除目录链接时不得遍历或删除其目标。共享测试与服务按已明确交接的资源窗口运行。

## 路径与配置

- `.ai-memory` 在本仓库指向相对路径 `.sop-runtime/ai-memory`。规则和能力声明位于当前项目内；不得重新指向其他工作区。
- 规约源码位于固定版本的 `ai-sop/`，运维源码位于固定版本的 `ai-sop-ops/`。统一hook的权威实现是 `ai-sop-ops/sop_ai_hook.py`。
- `ai_capabilities.json` 的来源是 `ai-sop-ops/AI_CAPABILITY_REGISTRY.json`。它声明能力与适配方式，不证明工具已经安装、hook已经绑定、凭证可用或执行验证通过。
- 可选 `hook_policy.json` 由团队明确维护；文件缺失时使用当前hook的内置策略，不为填齐文件而覆盖策略或启用新权限。

本规则初始集本身不代表产品全部完成，当前工作范围、待验事项和最近阶段以 `memory/current_state.json` 及对应阶段记录为准。
