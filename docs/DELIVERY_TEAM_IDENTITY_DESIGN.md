# 团队稳定身份与任务归属

## 目标与边界

任务负责人改名后仍是同一个人或 Agent；同名成员不能相互接管工作。停用、移出项目或重新分配后，原验收不能重新冒充当前有效交付。工具是资源，不能承担任务验收责任。团队角色说明与实际账户权限分别表达。

本阶段完成稳定归属和团队工作台。运行成员与 AgentProfile 的显式绑定作为下一独立增量，必须连同预览、派发、待运行重检和真实运行验证交付；本阶段不显示虚构的可执行状态。项目组合、归档、质量发布与部署运维仍在完整待办中。

## 规范模型

- `Task.owner_id` 是唯一任务归属源，空字符串表示未分配。人类身份来自当前项目授权范围中的 User/ProjectMember，Agent 和工具来自现有项目成员登记；不再创建镜像账号实体。
- 写接口只接受稳定 `owner_id`；省略表示保持，显式空字符串表示清空。`assigned_to` 是只读显示名称，不能写入、匹配、推断或授权。
- 现有 `DeliveryWorkspace.task_owners` 通过显式 schema apply 迁移到 SQL。只迁移同租户、同项目、真实 Task 的明确关联；悬空成员 ID 保留为不可用，名称不迁移为身份。迁移完成移除旧 map，避免双来源。
- 当前 owner 投影包含 `id/name/kind/active/available/reasons`；未分配为 null，缺失成员保留 ID 和具体不可用原因。任务选择器显示姓名、类型和稳定标识，失效的当前值仍能辨认。
- 证据保留原始显示名称作为审计事实；语义依据只使用稳定 ID、身份类型和有效性。改名不改变归属或使验收失效。停用、移除、换负责人会永久失效原凭据，恢复旧值也不能复活。
- 普通 CRUD、同步、导入和任务计划使用同一归属校验。自动治理任务缺少明确身份时保持未分配，不能将 Coder、Ops 等角色标签当作真实成员。
- 读取不修复数据库、不改 workspace version。写入维持项目权限、版本检查、幂等和已有进度记录事务边界。
- 旧的无版本 `tested_work` / `dependency_basis` hash 不自动重绑为新规范；需要重新评审，并保留原审计。读取按当前规范展示其失效状态，后续业务写入持久化。升级回执声明该边界，不增加旧 hash 比较或别名兼容层。

## 四个界面

1. 团队列表：紧凑成员卡，搜索、成员类型和登记状态筛选，真实责任任务数。清楚区分登记状态、日历信息与运行状态。
2. 成员详情：`team_member=<稳定ID>` 深链；身份、角色说明、任务和日历入口集中展示，关闭后恢复列表筛选。沿用现有 `member_id` 的日历筛选用途。
3. 负责人选择：共享呈现，姓名、类型、短标识区分同名；当前停用或缺失成员显示不可用原因并允许重新分配，工具不能选为责任人。
4. 执行计划：负责人独立于真实运行 Agent 和执行位置；继续使用现有显式运行配置与设备选择，不以登记名称自动匹配。

正常状态展示当前事实和可用操作；无成员与筛选无结果提供不同恢复动作；读取失败保留已读信息并可重试；权限不足只读、失效身份提示重新分配。390px 单列、弹层不溢出，键盘可进入详情、选择、保存和返回。
