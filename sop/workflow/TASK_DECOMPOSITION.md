# 任务拆解规范

## 拆解原则

1. **单一职责**：一个 Task 只做一件事
2. **独立可验证**：Task 完成后可以独立测试
3. **上下文可容纳**：Task 所需上下文 < 单个上下文窗口
4. **明确完成标准**：Task 有清晰的 Done 定义

## 拆解粒度标准

### 太粗（需要继续拆）
- "实现用户认证系统" → 包含多个独立功能
- "重构数据库层" → 影响多个模块
- "修复所有 Bug" → 多个独立问题

### 合适粒度
- "实现 JWT token 生成函数"
- "为 UserService.create 添加邮箱唯一性校验"
- "修复 #123：登录时 session 未清除的问题"

### 太细（可以合并）
- "添加 import 语句"
- "修改变量名"
- "添加一行注释"

## 拆解流程

### 输入：用户需求
```
需求：实现用户注册功能
```

### Step 1：识别功能边界
```
- 前端：注册表单 UI
- 后端：注册 API 端点
- 数据库：用户表结构
- 邮件：验证邮件发送
- 测试：各层测试
```

### Step 2：识别依赖关系
```
数据库迁移 → 后端 API → 前端表单
                      → 邮件服务（并行）
后端 API → 后端测试
前端表单 → 前端测试
```

### Step 3：输出任务树
```yaml
tasks:
  - id: T001
    title: "创建 users 表数据库迁移"
    type: infra
    estimate: S
    depends_on: []
    done_when: "迁移文件创建，本地 migrate 成功"

  - id: T002
    title: "实现 POST /api/v1/auth/register 端点"
    type: code
    estimate: M
    depends_on: [T001]
    done_when: "端点返回正确响应，输入校验通过"

  - id: T003
    title: "实现注册邮件发送服务"
    type: code
    estimate: S
    depends_on: [T001]
    done_when: "邮件模板创建，发送函数测试通过"

  - id: T004
    title: "实现注册表单前端组件"
    type: code
    estimate: M
    depends_on: [T002]
    done_when: "表单提交成功，错误状态正确显示"

  - id: T005
    title: "编写注册 API 集成测试"
    type: test
    estimate: S
    depends_on: [T002, T003]
    done_when: "正常注册、重复邮箱、无效输入三个场景测试通过"
```

## Task 模板

```markdown
## Task ID: T{number}

**标题**: [动词 + 对象，如"实现 X"、"修复 Y"、"添加 Z"]

**类型**: code | test | infra | doc | refactor

**估算**: S(<2h) | M(<1d) | L(需拆分)

**依赖**: [T001, T002] 或 []

**上下文**:
- 相关文件: [文件路径列表]
- 相关函数: [函数名列表]
- 背景说明: [1-2句话]

**实现要点**:
- [ ] 要点1
- [ ] 要点2

**完成标准 (Done When)**:
- [ ] 构建通过
- [ ] 测试通过
- [ ] [具体功能验证点]

**注意事项**: [可选：特殊约束或风险]
```

## 常见拆解模式

### 新功能拆解模式
```
数据模型 → 数据访问层 → 业务逻辑层 → API层 → 前端 → 测试
```

### Bug 修复拆解模式
```
复现 → 根因分析 → 修复 → 回归测试
（通常是单个 Task，除非根因复杂）
```

### 重构拆解模式
```
# 绞杀者模式：新旧并存，逐步迁移
创建新实现 → 添加适配层 → 迁移调用方（逐个）→ 删除旧实现
```

## 任务优先级规则

```
P0: 阻塞其他任务的基础设施任务
P1: 核心功能路径上的任务
P2: 非核心但用户可见的功能
P3: 优化、重构、文档
```

调度顺序：P0 → P1 → P2 → P3，同优先级按依赖关系排序。
