# 上下文预算管理

## 为什么需要预算管理

LLM 上下文窗口是有限资源。超出预算导致：
- 早期信息被截断（丢失关键上下文）
- 推理质量下降
- Token 成本激增
- 智能体行为不可预测

## 预算分配表

| 角色 | 最大预算 | 系统提示 | 任务上下文 | 代码/文件 | 历史对话 |
|------|---------|---------|-----------|---------|---------|
| Orchestrator | 50K | 5K | 10K | 15K | 20K |
| Planner | 30K | 3K | 10K | 12K | 5K |
| Worker/Coder | 40K | 3K | 5K | 25K | 7K |
| Reviewer | 20K | 2K | 3K | 13K | 2K |
| Tester | 25K | 2K | 5K | 15K | 3K |
| Debugger | 35K | 3K | 5K | 20K | 7K |

## 预算监控规则

### 警戒线（70% 预算）
- 停止读取新文件
- 开始压缩历史对话
- 将当前状态写入记忆系统

### 红线（85% 预算）
- 立即将关键状态持久化
- 完成当前原子操作后停止
- 向 Orchestrator 报告需要新上下文窗口

### 超限处理
1. 持久化当前所有状态
2. 创建"续接任务"（包含恢复所需的最小上下文）
3. 在新上下文中恢复工作

## 上下文加载优先级

加载文件时按以下优先级，预算不足时从低优先级开始裁剪：

```
P1（必须）：当前任务描述、相关函数签名
P2（重要）：被修改文件的完整内容
P3（有用）：相关测试文件
P4（参考）：类似功能的实现示例
P5（可选）：完整的历史对话
```

## 上下文压缩策略

### 对话历史压缩
- 保留：决策点、错误信息、用户明确指令
- 压缩：中间推理过程、重复的工具调用结果
- 删除：已完成任务的详细执行日志

### 代码上下文压缩
- 只读相关函数，不读整个文件
- 用函数签名替代函数体（当不需要实现细节时）
- 用 `grep` 结果替代完整文件读取

### 压缩触发条件
```python
if current_tokens > budget * 0.7:
    compress_conversation_history()
if current_tokens > budget * 0.85:
    persist_state_to_memory()
    request_new_context_window()
```

## Token 优化技巧

1. **精确读取**：`Read(file, offset=100, limit=50)` 而非读整个文件
2. **grep 优先**：先 grep 定位，再精确读取
3. **子智能体隔离**：探索性任务用子智能体，结果摘要返回主上下文
4. **增量更新**：用 Edit 而非 Write（只发送 diff）
5. **避免重读**：已读文件的内容记录在工作记忆中，不重复读取
