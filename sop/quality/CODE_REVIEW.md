# 代码审查规范

## 审查流程

```
提交 PR → Reviewer 读取 diff → 逐项检查 → 输出结论
```

审查者只读 diff，不读整个代码库（节省上下文）。

## 审查清单

### 1. 功能正确性
- [ ] 实现符合任务描述的需求
- [ ] 边界条件处理正确（空值、零值、最大值）
- [ ] 错误路径有合理处理
- [ ] 没有明显的逻辑错误

### 2. 安全性（必须全部通过）
- [ ] 无 SQL 注入风险（使用参数化查询）
- [ ] 无命令注入风险（用户输入不直接拼接命令）
- [ ] 无 XSS 风险（输出正确转义）
- [ ] 无硬编码密钥/密码/token
- [ ] 敏感数据不写入日志
- [ ] 认证/授权检查在正确位置

### 3. 性能
- [ ] 无明显的 N+1 查询
- [ ] 循环内无不必要的 I/O 操作
- [ ] 大数据集使用分页或流式处理
- [ ] 无内存泄漏风险（资源正确释放）

### 4. 代码质量
- [ ] 函数/变量命名清晰，无需注释即可理解
- [ ] 函数长度合理（通常 < 50 行）
- [ ] 无重复代码（DRY，但不过度抽象）
- [ ] 无死代码（未使用的变量、函数、import）
- [ ] 符合项目现有代码风格

### 5. 测试
- [ ] 新功能有对应测试
- [ ] Bug 修复有回归测试
- [ ] 测试覆盖正常路径和错误路径
- [ ] 测试名称清晰描述测试场景

### 6. 最小化原则
- [ ] 没有超出任务范围的变更
- [ ] 没有未请求的重构
- [ ] 没有未使用的新依赖

## 审查结论格式

### PASS
```
REVIEW: PASS
Task: T{id} - {title}
Commit: {hash}
Notes: [可选：值得注意的点，但不阻塞合并]
```

### NEEDS_CHANGES
```
REVIEW: NEEDS_CHANGES
Task: T{id} - {title}
Commit: {hash}

必须修复（阻塞合并）:
1. [文件:行号] [问题描述] [修复建议]
2. ...

建议改进（不阻塞）:
1. [文件:行号] [建议]
```

## 审查严重级别

| 级别 | 描述 | 处理方式 |
|------|------|---------|
| BLOCKER | 安全漏洞、数据丢失风险、功能错误 | 必须修复后重新审查 |
| MAJOR | 性能问题、测试缺失、代码质量严重问题 | 必须修复 |
| MINOR | 命名不佳、小的代码风格问题 | 建议修复，不阻塞 |
| NIT | 个人偏好 | 可忽略 |

## 自动化检查（审查前必须通过）

以下检查由 CI 自动完成，审查者无需手动检查：
- 代码格式（linter）
- 类型检查（TypeScript/mypy）
- 单元测试
- 依赖安全扫描（npm audit / pip-audit）

**CI 未通过的 PR 不进入人工审查。**
